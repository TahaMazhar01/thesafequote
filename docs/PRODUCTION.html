Production deployment and filtered exports

Release preparation · 10 October 2026

A successful GitHub push does not provision PostgreSQL, transfer the local database, install certificates or create production administrators. The current app requires a Node.js server with PostgreSQL and persistent media storage. A static frontend-only host cannot run these backend routes. Verify the hosting configuration before switching the live deployment branch.

Lead downloads

Dashboard → Leads → apply search/status/view and received-date filters → choose Excel or CSV → Download leads. All matching results are included, independently of pagination, newest first. Maximum 2,000 leads and an 8 MiB raw-data budget per request; narrow the period if exceeded. Five export requests per five minutes per account. Exports are private authenticated POST responses with no-store headers and an audit entry recording actor, format and count without search terms.

Excel has styled headers, frozen first row, filters and text cells preserving phone numbers and leading zeroes. CSV is UTF-8 with BOM and escaped cells; potentially executable formula prefixes are neutralized. Values are not truncated to the 120-character table preview. Current fields appear first with historical removed fields appended. Current labels are used for existing field IDs; an export is not an exact historical form-label archive. Local timezone and UTC received timestamps are both included. Exact-time filters use the browser timezone and an exclusive end time. Date-only filters include the whole final day in ADMIN_TIMEZONE. Apply changed filters before downloading.

Hosting requirements

  • Node.js 24 with npm. Install from the committed lockfile using npm ci.
  • PostgreSQL on a private interface with a dedicated database. Same-host loopback is supported. Remote connections require DB_TLS=verify with trusted CA verification.
  • Persistent writable directory outside the release checkout for BLOG_UPLOAD_DIR. Default media budget is 512 MiB and 5,000 WebP files. Across multiple processes the database advisory lock serializes quota checks; all instances must share the same storage.
  • HTTPS reverse proxy. Example Caddy and Linux service templates are in deploy/. They have not been installed or validated on the user's server.

Initial rollout order

  1. Create database and separate owner/migration and runtime accounts. Keep database/firewall private. Store credentials in the hosting secret manager or restricted environment files, never GitHub source files.
  2. In a controlled maintenance process supply MIGRATION_DATABASE_URL, DATABASE_URL and auth settings; run npm run db:migrate. This applies Better Auth and ordered application migrations. Then apply db/production-grants.sql using psql against the intended database after separately creating fa_runtime. The local provisioning script is restricted to fa_local and is not a production provisioning command.
  3. Create a new production admin using npm run admin:create with ADMIN_EMAIL and ADMIN_PASSWORD supplied securely and NODE_ENV=production. Do not copy the local admin-login file or seed dummy leads. Published local blog/form content is database data and needs an intentional migration or reseeding review; git push alone does not transfer it.
  4. Remove MIGRATION_DATABASE_URL and ADMIN_PASSWORD from the web runtime environment. Keep maintenance credentials in a separate operator context. Build with the final public URL: npm run build.
  5. Run the application as an unprivileged service behind HTTPS. npm start runs startup gates. The initial enrollment exception allows login and /admin/security while production data APIs deny unenrolled admins.
  6. Sign in and enroll the authenticator. Store recovery codes privately. Run npm run security:production-check without the enrollment exception. All active admins must be enrolled.
  7. Run npm run verify:deployment -- https://YOUR_DOMAIN. Verify form submission persistence, dashboard permissions, Excel/CSV exports, Secure cookies, recovery login and real client-IP limits against the deployed server.
  8. Only switch live traffic after a backup/restore test, resource test and health checks pass. Keep the previous release available; roll back code if startup or health fails. Do not blindly reverse database migrations or remove live leads.

Operational release requirements

Schedule the maintenance command using the host scheduler and its separate credentials. Alert on /api/health failures, auth failures, disk budget, memory, latency and PostgreSQL connection saturation. Store encrypted offsite database and media backups; test restoration into a separate database. Define lead and audit retention with the business owner before implementing destructive cleanup. OS disk encryption, offsite backup configuration and an external load test remain unverified locally.

SEO

/robots.txt is generated at request time. Development, HTTP and explicitly disabled staging environments disallow crawling. Public HTTPS production allows public pages and blog images and disallows /admin and /api/. Admin pages also carry noindex metadata. Robots is crawler guidance, not a security boundary.

/sitemap.xml includes the public static pages and published non-deleted blog posts. Drafts, trash and admin pages are excluded. Static pages no longer advertise a false changing lastmod; blog entries use their stored updated_at. The configured origin is normalized. The current single sitemap supports up to 49,000 blog posts; split it before exceeding this scale. Submit the deployed sitemap to Search Console after verification.
